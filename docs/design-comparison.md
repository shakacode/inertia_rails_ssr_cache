# Arena cross-judgment

This comparison records the design-stage decision. The final contract and resolved
proof requirements are in [architecture](architecture.md).

Read both candidates against the five-item rubric. Scores assess the proposed architecture, not completed implementation or production proof. Both use the same model family under the local harness; this is an independent artifact comparison, not cross-provider validation.

## Pick

Choose **A as the only transport**. Its boundary matches the requested small Active Job gem and allows proof using released Inertia behavior without introducing a remotely accessible diagnostic protocol. Keep B as a documented alternative for a future adopter with a demonstrated need to exercise the deployed web tier. Do not implement both behind an abstraction.

Parent feasibility evidence supports this choice: A local feasibility script with Rails 8.1.4, inertia_rails 3.22.0, `Rack::MockRequest`, explicit Host/Accept, and a fake SSR HTTP endpoint observed first miss, second same-key hit and one renderer call. This proves the request/cache seam only; it is not real React rendering, concurrent isolation or cross-process shared-cache proof.

## Valuable grafts only

1. **Precise failure outcomes from B.** Preserve distinctions between HTTP failure, missing native-cache evidence, changing cache identity and release mismatch. These make failure actionable without exposing page props or HTML. Keep one owner of result interpretation in Probe; no extra result-processing layer.
2. **Boundary validation detail.** Explicitly reject backslashes, control bytes, protocol-relative targets and origin userinfo/query/fragment. Fresh request construction must be structural, with no caller-supplied cookies or authentication headers.
3. **B's cached-build-evidence concern, not its signed protocol.** A Node callback guard checks only cache misses. For the first version, document clean immutable release identity and guarded SSR artifacts as preconditions, and prove them with changed-release/rollback integration tests. If the public result claims it certifies the actual cached Node build, then a minimal embedded build marker or equivalent independently verifiable evidence becomes necessary. Do not make that stronger claim from cache-hit evidence alone. A marker can be reconsidered without adopting HTTP, signing or observer middleware.
4. **Deadline terminology.** Retain A's truthful target/concurrency bound and explicitly separate it from wall-clock bounds. Do not borrow B's “60-second” promise for in-process Rack work or use asynchronous Ruby timeouts around Rails.

## Red flags to resolve during implementation

- **Status and cache hit are conjunctive requirements.** The spike demonstrated that an SSR cache entry can be populated before a failing Rails layout produces HTTP 500. Require successful HTML responses for both probes plus same-key second-hit evidence; never return success from the cache event alone.
- **Request-local attribution must actually work under concurrency.** A global subscriber filtered only by thread is insufficient for fiber-concurrent execution. Match the operation's execution context, unsubscribe/clear in ensure, and cover a failure plus overlapping requests in tests.
- **Shared-cache proof cannot be replaced by MemoryStore tests.** Use separate Rails processes and a common real retaining store for visitor reuse. FileStore is enough for a portable integration fixture if both processes share the same directory and configuration.
- **Do not trust fake SSR HTML as the final runtime proof.** Retain the spike for diagnosis, then run a released Inertia JS callback with React SSR and assert body/head, renderer calls, build rejection and independent visitor reuse.
- **Declared support must match tested releases.** Cap initial Inertia adapter compatibility to verified released behavior and compile the npm wrapper against an actual released callback. Development master notifications are unavailable in 3.22.0.
- **Blanket `untyped` or lint exceptions would hollow out the bootstrap.** Keep the pure plan/proof logic type checked and framework boundaries narrow. Run the configured gates; do not inherit disabled Steep or advisory-only security checks from RoR.
- **No new public batch/run registry.** The selected sketch needs neither polling handles nor a persistent completion database. A job identifier is an enqueue receipt, not warm readiness.
